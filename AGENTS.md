# ccluster — Agent Guide

Two Kubernetes operators from one Go module, with a Helm chart catalog and generated
Python models. Read [README.md](README.md) for the project and local quickstart.
This repository's conventions take precedence over generic kubebuilder scaffolding.

## Repository map

| Path | Purpose |
| --- | --- |
| `cmd/ccluster-{cp,ip}-operator/` | Separate binaries for separate clusters; cp drives Argo CD, ip verifies `catalogs/cluster_base` against `CCLClusterConfig`. |
| `internal/controller/{cp,ip}/` | Per-operator controllers; shared bootstrap is in `internal/manager/`. |
| `internal/registry/` | Generic per-chart registry (chart path → function) and the `*_registry` packages built on it, such as the ip operator's `verifier_registry` and the cp operator's `drift_registry`. |
| `api/ccluster/v1alpha1/` | CRD types; API group is `ccluster.nvidia.com`. |
| `pkg/client/` | Generated Go clientset, apply configurations, listers and informers for the API types, for programs outside this repository and for the cp operator's infra-plane watch in `internal/remote/`; `test/client/` tests them. |
| `internal/argocd/v1alpha1/` | Hand-written partial Argo CD API mirror; extend it rather than using `unstructured`. |
| `config/` → `charts/{cp,ip}/chart/` | Kustomize sources → generated operator Helm charts. Deploy with Helm. |
| `catalogs/` | Helm charts with typed Go values, part of the Go module: `cluster_base/` platform components (each registered with a `Verifier` the ip operator runs), `deployments/` tenant workloads, `resources/` the queues and volumes they use. A chart that runs a binary built here keeps its source in a subdirectory, such as `deployments/compute_deployment/compute-ssh/`. |
| `hack/pyschema/` → `python/` | CRD spec/status and chart values → JSON Schema → Pydantic package. |
| `examples/` | Hand-written example CRs. |

## Architectural guardrails

- Argo CD runs only in the control-plane cluster and is installed by the cp Helm chart.
  The operator creates Applications; it must never install or upgrade Argo CD itself.
- Managed Argo CD resources use ownership annotations and `ownedBy` checks, never owner
  references. Applications require explicit, reverse, one-at-a-time teardown.
- Rollout order is list position. Release is monotonic: degradation must not withdraw an
  already released Application. Do not introduce ApplicationSet or RollingSync.
- Preserve namespace isolation: Applications live beside their CCLComponentSet; cluster
  Secrets and AppProjects live in the Argo CD namespace. Projects allow only the catalog
  repository, and cluster Secrets are project-scoped.
- `CCLInfraPlane Available=True` guarantees its namespace's AppProject already exists.
- Keep cp/ip RBAC separate and their leader-election IDs distinct.
- The ip operator verifies `cluster_base` and never installs, upgrades or deletes anything.
  Verifiers read live objects, never Argo CD or Helm release state. Its RBAC is read-only
  apart from `CCLClusterConfig` status; a Verifier reading a kind adds a marker in
  `internal/controller/ip`.

## Source of truth and generation

Never hand-edit generated CRDs, the operators' generated RBAC roles, `zz_generated.*.go`,
`PROJECT`, operator chart `templates/` or `.helmignore`, the Go client in `pkg/client/`, or generated Python modules. Edit their sources and regenerate.
`charts/cp/chart/Chart.lock` is generated by `make helm-deps-update-cp`.

Operator-chart `Chart.yaml` and `values.yaml` are preserved and may be edited. Kustomize
inputs are hand-written. Python's hand-written files are documented in
[Development](docs/development.md#python-generation).

| Changed input | Regenerate |
| --- | --- |
| API types, markers or API doc comments | `make manifests generate`, `make client-generate`, `make helm-generate`, `make python-generate` |
| `config/` or RBAC markers | `make helm-generate` (includes manifest generation) |
| Catalog Go values or their comments, or `hack/pyschema/` | `make python-generate` |
| `hack/clientschema/` | `make client-generate` |

Commit the resulting generated changes. API and catalog doc comments ship in schemas;
comment-only edits can require regeneration too. Do not install CRDs into a cluster merely
to regenerate files.

## Implementation and validation

- Follow Kubernetes API conventions: standard types such as `metav1.Time`,
  `metav1.Condition`, and current `observedGeneration` on conditions and status.
- Keep reconciliation idempotent and watch-driven; preserve the explicit teardown retry.
- Log messages are capitalized, past tense, without a trailing period, with the object
  type named and balanced key-value pairs.
- For Go changes run `make fmt vet lint-fix` and `make test`. Validate changed charts with
  `make helm-lint` and changed Python models with `make python-test`.
- New controller behaviour belongs in envtest. Use selective table tests for states
  envtest cannot cheaply reach. Test contracts, not implementation details.
- Envtest does not prove RBAC or running watch wiring; use `make test-e2e` for those.
  `make test-e2e-full` adds real Argo CD reconciliation. See the testing guide for setup.
- Run checks appropriate to the changed inputs, including required generators. Report
  what ran and any checks that could not run; the commit skill has the pre-commit matrix.

## Cluster safety

- Pin the intended cluster with a dedicated `KUBECONFIG` before cluster operations.
  Helm targets also accept `KUBE_CONTEXT_CP` / `KUBE_CONTEXT_IP`; do not put flags in
  `KUBECTL`. Standalone `deploy-cp` / `deploy-ip` otherwise use the current context.
- Helm owns deployed CRDs: do not run `make install` before `make deploy-cp`. Existing
  CRDs can be adopted with `make helm-adopt-crds-cp`; see the development guide.
- Deleting a CRD deletes its CRs. `make undeploy-cp` keeps CRDs but removes bundled Argo CD;
  finish required CR teardown while the controllers still run.
- `make clean` deletes development clusters; `make clean-all` also removes tools and
  build output. E2e creates and deletes its own cluster: never use a working cluster as
  `KIND_CLUSTER_E2E`.
